## 0. 先读这一节

### 0.1 作品要证明什么

轮腿机器人在月面行驶：

- 平时用轮子，又快又省；
- 遇到只看得见正面的石头，用 Lux3D 把背面想象出来，在月壤物理里把可选动作预演一遍，再做决定。

核心论点：

- **只看正面的机器人，按保守规则处理看不见的地方，安全但吃亏**：绕远路、抬着身子慢慢挪，或者停下。
- **想象出背面，就能在安全的前提下把这些亏省下来。**

### 0.2 已经确认的事实（不要重做）

- 配准入口已修好（三角形 z-buffer 评分、只用可见面精修、保留最好姿态），真值网格走正常粗搜索后 IoU 0.96、深度 P95 19.9 mm。
- 统一任务终点（`wheelleg_env._task_check`）已生效；步数上限截断不再记成翻车。
- 真值当先验时，生成部分 100% 进入决策几何（`docs/evidence/v0/tparent_*.json`）。
- BODY_CLEARANCE 零机身接触可用，但统一终点下要 113–117 s。
- 价值上限已有初步证据（`runs/v3/stage010/g1v2_summary.json`）：len_short、len_mid 两个变体中，完美想象选 D2，约 7 s；只看正面（保守）选 BODY，约 114 s；两者都安全。
- 真实 Lux3D 候选在 moon_rock_05 上后缘偏短（1.04–1.13 m，真值 1.165 m），属于偏乐观。

### 0.3 这份 SPEC 纠正的三件事

1. **候选准入不再用可见面拟合门槛**（IoU ≥ 0.90、深度 P95 ≤ 20 mm）。这条门槛只用于回归测试里测配准入口本身。候选准入改为"与观测不矛盾"，见 §2.4。
2. **先做大样本"想象体检"**，弄清 Lux3D 在哪类石头上靠得住、偏向哪边，再谈方法收益。
3. **停止基础设施打磨**：缓存身份、溯源清单、发布包、只读复核这类工作一律不做，除非它直接影响某个结论。

## 1. 硬约束（不可改）

1. API 密钥只从环境变量读取，不打印，不写进文件、命令行或任何打包。
2. Lux3D 调用每次记账（`ledger.jsonl`）。积分不设限。服务端失败可以重提一次，并标 `retry_of`；第二次失败记为失败。客户端错误先修好再提交。
3. 所有动作在 MuJoCo 加 Bekker–Wong 月壤里真实执行。月面重力 1.62，主条件 nominal：kc 1400、kφ 820000、c 170 Pa、φ 35°、k_shear 0.018。不允许运动学瞬移，也不允许用脚本摆姿态。
4. 动作参数只能读可见观测和想象出来的几何，不能读真值。真值只用于执行与评估。
5. 场景变体只允许修改未知区 U：U 外异或必须为 0，不得往已知空地里加占据，V 壳层必须保持被支撑。
6. 不修改任何已冻结的旧产物（`runs/v3/stage0xx/` 下已提交的文件）。新输出一律写到 `runs/v4/<WP>/...`。
7. 不对 `main` 强推。每个工作包完成后推送一次。
8. 有限尝试：同一个技术难点，两条实现路径都按计划失败，就停下，写进报告，不再调参。

## 2. 共用定义

### 2.1 各臂（arm）

| 名称 | 几何 | 用途 |
| --- | --- | --- |
| `PERFECT` | V ∪ (T ∩ U)，真值补全未知区 | 方法上限 |
| `FULL` | V ∪ (P ∩ U)，P 为通过准入的真实 Lux3D 候选 | 方法本身 |
| `OBS_CONS` | V，未知区按保守处理 | 主对照：只看正面 |
| `OBS_OPT` | V，未知区当空地 | 参照：说明"看不见就当没有"会出事 |
| `WHEEL_ONLY` | 动作集只含轮式动作 | 腿式场景的对照 |

### 2.2 未知区的保守处理（OBS_CONS 和 FULL 共用同一规则）

既没看到、也没被通过准入的想象覆盖的未知体素，按"可能有障碍"处理。具体做法沿用现有 BODY 计划里的 `unknown_hold`：抬身一直保持到 `lower_at = 2.45 m`。绕行路径经过未知体素就判不安全。若要改规则，先写进 `configs/v4_protocol.json` 再用。

### 2.3 结局与代价

- **结局**：`pass` / `safe_stop` / `fail`（翻车、卡住、机身接触、超时）。由统一的 `_task_check` 判定：终点 2.6 m、稳定 1 s、通道半宽 1.2 m、预算 120 s。
- **代价**：用时 `t_end`、行驶路程、能耗（各关节 |τ·ω| 积分，加上轮子的同一项）、停车次数、机身接触次数。

### 2.4 候选准入（替代旧门槛）

一份候选必须同时满足以下五条才算通过：

1. 配准收敛，尺度比在 0.8–1.25；
2. P∩U 非空，并且和 V 壳层相接（相接比例的容差待标定）；
3. 侵入已知空地的比例不超过 2%；
4. 投影轮廓和观测轮廓没有大面积冲突（容差待标定）；
5. 数据完整。

- 待标定的容差，用"真值当先验"和 2–3 个扰动先验（平移 ±2 cm、缩放 ±10%）来标定。标定后写入 `configs/v4_admission.json` 并冻结，不随批次调整。
- 可见面 IoU 和深度 P95 照常记录，**只报告，不拦截**。

### 2.5 决策

- 主规则：每份通过准入的候选各跑一个预演矩阵，多数（≥ ⌊n/2⌋+1）判定安全的动作里，选代价最低的。
- 同时按最坏规则（n/n）选一次。两个选择不同时，**两个都要在真值上执行**并报告。
- 零候选通过时：FULL 回退为 OBS_CONS，并标注 `fallback_reason`。
- 决策先落盘，再执行。

## 3. 工作包

### 执行顺序

1. 先做 WP0 和 WP1，完成后回报一次；
2. 然后三条线同时推进，沙箱里重任务并发不超过 2 个，Lux3D 等待期间跑仿真：
   - 想象线：WP2 → WP3 → WP4
   - 腿和软土线：WP5、WP6
   - 生产线：WP7、WP8

### WP0 数据可取回

- **内容**：把现有原始 GLB 和 results.zip 推到 GitHub，用 Git LFS（跟踪 `*.glb`、`*.zip`）或 Release 附件。范围：
  - stage007 的 6 个候选；
  - stage013 输入改进批次的 5 个；
  - v3 的全部候选；
  - `gen_v2/P58_S2`。

  同时生成 `dist/v4/glb_manifest.json`，内容包括任务号、路径、sha256、来源岩石、视角、裁剪方式。
- **验收**：在一个新目录里 `git clone` 加 `git lfs pull`（或下载 Release）后，清单里所有文件的 sha256 都对得上。
- **权限不够怎么办**：立即停下，写 `docs/v4/BLOCKER_DATA.md`，说明缺什么权限。不要改成只留在本机。

### WP1 回归测试

- **内容**：编写 `scripts/v4_regress.py`，一条命令跑完以下检查，输出 `runs/v4/regress/<时间戳>.json`，逐项给出 pass/fail：

  | 编号 | 检查内容 | 通过标准 |
  | --- | --- | --- |
  | T1 | 真值当先验 | 至少 1 个状态的隐藏区 IoU = 1.0，并通过 diff⊂U 断言 |
  | T2 | 配准已知答案 | 真值网格放到任意局部坐标后走配准入口：IoU ≥ 0.90，深度 P95 ≤ 20 mm |
  | T3 | 统一终点 | len_short 上 D2 和 BODY 都触发 success，`t_end` 等于最后一帧时间 |
  | T4 | 步数上限 | 人为设置过小的上限后，结果记为截断，不记为 fail |
  | T5 | 预演与执行一致 | 同一 S0 下 project 与 same_scene 的前 50 步 qpos 一致（warmstart 已清零） |
  | T6 | 记录完整 | 不低于 50 Hz，字段齐全（qpos、qvel、动作、关节目标、接触、阶段、轮下陷、滑移率） |

- **验收**：六项全部通过。
- **之后**：每个正式批次开跑前都要跑一次，结果文件路径写进该批报告。

### WP2 背面价值上限（G1）

- **第一步：确认已有结果。** 在统一终点下重跑 ref、len_short、len_mid、len_long、rear_low、rear_high，臂为 PERFECT、OBS_CONS、OBS_OPT。从同一个 S0 出发，选中的计划在完整真值场景上执行。
  - 输出 `runs/v4/wp2/confirm_table.csv`，每行一个场景 × 臂，列出：决策、结局、全部代价项。
- **第二步：扩展。** 在至少 3 块不同岩石上构造只改 U 的变体族，至少覆盖 3 种类型：
  - 背面短 → 绕行更省；
  - 背面不高 → 抬身能过；
  - 背后通道被挡 → 提前避开死路。
- **验收**：至少 6 个"PERFECT 比 OBS_CONS 更省或更安全"的场景，来自至少 3 块岩石。输出 `runs/v4/wp2/value_scenes.json`，列出这些场景和差距大小。
- **找不够怎么办**：回报找到了哪些、在哪里卡住。

### WP3 想象体检（G2）

- **范围**：8 块岩石（`moon_rock_01`…`07`、`rock_07`）× 3 个视角 × 每个视角 6 份候选，共 144 个任务。
  - 视角在开跑前固定：建议偏航 0°、+25°、−25°，相机高度和距离沿用现有观测。
  - 裁剪方式 3 种：raw、white、masked，每种采样 2 次。
  - 裁剪不低于 512 px，不做放大。
  - G1-Turbo，faceCount 30000。
- **每份候选的流程**：配准（固定入口）→ 融合 → 准入判定（§2.4）→ 测量下列量，并且全部带符号：

  | 量 | 计算方式 | 偏乐观 | 偏保守 |
  | --- | --- | --- | --- |
  | 后缘位置误差 | 候选 − 真值，单位 m | 负 | 正 |
  | 隐藏最高点误差 | 候选 − 真值，单位 m | 负 | 正 |
  | 左右绕行带占据 | 沿 D1/D2 的走廊带，统计"候选说空、真值有"和"候选说有、真值空"的体素比例 | 前者 | 后者 |
  | 隐藏区体积比 | 候选 ÷ 真值 | — | — |
  | 拟合指标（只报告） | 可见面 IoU、深度 P95 | — | — |

- **每个岩石 × 视角汇总**：6 份候选之间的分歧（各量的极差）、多数意见的误差、最坏意见的误差。
- **第二眼子集**：挑分歧最大的 4 个岩石 × 视角，横移约 0.3 m 拍第二张，用 imgs 两图生成 2 份，比较误差和分歧的变化。
- **输出**：
  - `runs/v4/wp3/candidates.csv`：每行一份候选；
  - `runs/v4/wp3/summary.json`；
  - `runs/v4/wp3/plots/*.png`：误差分布、偏向、分歧与误差的关系。
- **验收**：8 块岩石全部完成；`summary.json` 能回答三个问题：哪类石头靠得住、整体偏向哪边、分歧大小能否预示误差。
- **需要立即回报**：多数意见的后缘误差中位数偏短超过 3 cm，或者绕行带"候选说空、真值有"的比例中位数超过 5%（即系统性偏乐观）。

### WP4 真实想象的价值（G4）

- **依赖**：WP2 的价值场景，加上这些场景所用岩石的 WP3 候选。必要时为这些场景补生成。
- **内容**：每个价值场景跑 FULL、OBS_CONS、PERFECT、OBS_OPT。FULL 同时报多数规则和最坏规则两种选择，选择不同就两个都执行。
- **指标**：差距拿回比例 = (OBS_CONS 代价 − FULL 代价) ÷ (OBS_CONS 代价 − PERFECT 代价)。按场景给出，再给中位数。
- **验收**：输出 `runs/v4/wp4/table.csv`。表里如实列出：FULL 更省的场景、FULL 与 OBS_CONS 相同的场景、FULL 出现翻车或卡住的场景（每个都附原因）。

### WP5 软土抬轮脱困（G3）

- **场景**：平地中段 1.5 m 长的软土区。参数由你定，但必须明显更软（例如 kφ、c 大幅降低），写入 `configs/v4_soil_soft.json`。
- **对照**：WHEEL_ONLY 以常规速度驶入，在 3 个初态中至少 2 个出现卡住：10 s 内前进不到 0.1 m，且滑移率 > 0.8。
- **动作 `SOFT_ESCAPE`**：检测到下陷或打滑后，逐轮抬起、前移、放下（轮步），配合其余三轮驱动，直到驶出软土区。用逐关节控制实现（可复用 `v3_basic_cycle.py` 的支撑转移）。
- **验收**：3 个初态中至少 2 个脱困成功，并到达软土区后 1 m。记录每个轮子的下陷深度和滑移率。
- **有限尝试**：两种实现路径都失败，就停下回报。

### WP6 抬身跨越提速

- **目标**：在 ref 和 len 系列场景上，BODY_CLEARANCE 的统一终点用时 ≤ 40 s（现在 113–117 s），机身接触仍为 0。
- **可调**：行驶速度、抬升和放下的斜坡时间、`lower_at` 计算。不改抬升高度上限。
- **验收**：ref、len_short、len_long 三个场景达标。
- **有限尝试**：同上。

### WP7 不依赖想象的展示墙素材

- **类别 A 轮式行驶，4 个场景**：
  - 松软平地巡航 10 m，留下下陷和滑移记录；
  - 碎石区（低于轮半径的真实扫描小石块）直接碾过；
  - 缓坡上下（±8°）；
  - 同一段 5 m 路，轮式与抬轮步进各跑一次，对比速度和能耗。
- **类别 B 绕行决策，2 个场景**：
  - 开阔巨石，绕近的一侧；
  - 一侧是坑，绕另一侧。

  两个场景都由决策逻辑自动选择，并记录各选项代价。
- **每个场景**：按 §4 完整记录，障碍同时保存碰撞表示和带贴图的视觉网格。
- **验收**：6 个场景全部有完整记录和清单。

### WP8 完整任务路线骨架

- **地形**：约 20 m 路线，地形跨度 ≥ 25 m，`field_x_max` 足够大。包含：
  - 着陆器（静态模型）和采样点标记；
  - 一侧陨石坑、一段软土区、散布碎石；
  - 5 个遭遇位：开阔巨石、一侧有坑的巨石、软土段、想象分歧的石头、两侧封死的窄通道。
- **第一版**：遭遇处先接现有能力（轮式加绕行加 BODY，用 OBS_CONS 决策）。验证整段一次连续执行，并按 §4 记录。
- **之后**：WP3–WP6 完成后，把 FULL 决策、软土脱困、第二眼接进来。
- **验收**：一次连续执行从起点到采样点（或者在某个遭遇处安全停下），完整记录并附场景文件。

## 4. 记录与目录规范

```
runs/v4/<WP>/<scene_id>/
  scene.json            # 场景规格：地形、障碍位姿、月壤分区、种子、代码提交号
  assets/               # 障碍碰撞表示 + 带贴图视觉网格（obj/glb + 贴图）及位姿
  observation/          # 相机 RGB-D、裁剪图、相机内外参
  candidates/<task_id>/ # 原始 GLB、配准矩阵、准入判定、体检测量
  <arm>/decision.json   # 所有选项的安全判定、代价分项、选择与理由、想象分支
  <arm>/record/         # ≥50 Hz：qpos、qvel、动作、各关节目标、接触、阶段、轮下陷、滑移率
  <arm>/result.json     # 结局与全部代价项
  manifest.json         # 文件清单与 sha256
```

- 预演矩阵的每一格都保留轨迹引用，不只保留关键格。
- 每次 Lux3D 调用记录以下字段：提交、完成、取回的时刻，任务号，版本，模式，上传原图，返回 GLB，面数，是否重提。
