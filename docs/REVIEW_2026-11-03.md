### P0-3 可见门测的是观测壳层，不是生成几何（本批最强的负面证据）

`reports/v2/key_states/*.multi.json` 里，`visible_quality` 同时给了配准（候选自身）与融合后两组指标：

| 状态·候选 | 配准 IoU | 配准 P95 | 配准判定 | 融合后 IoU | 融合后 strict |
| --- | --- | --- | --- | --- | --- |
| P58·S2·C1 | **0.394** | 25.3 mm | 失败 | **0.9863** | **通过** |
| P58·S2·A1 | 0.477 | 36.4 mm | 失败 | 0.9722 | 通过 |
| P06·S1·A1 | 0.589 | 40.0 mm | 失败 | 0.9236 | 通过 |
| P06·S1·C2 | 0.710 | 26.2 mm | 失败 | 0.9181 | 不通过 |

把范围扩到全部 5pt 状态（56 个候选有配准指标，其中 50 个同时有融合后指标）：

| 指标 | 值 |
| --- | --- |
| 配准 `align_pass` | **0 / 56** |
| 融合后 `fused_strict_pass` | **47 / 56** |
| 配准 IoU 范围 | 0.322 – 0.882（std 0.145） |
| 融合后 IoU 范围 | **0.918 – 0.986（std 0.021）** |
| Pearson r（配准 vs 融合） | **0.152** |
| Spearman ρ | **0.176** |
| 线性拟合 | `fused_iou ≈ 0.945 + 0.022 × align_iou` |

最后一行是结论：**截距 0.945 来自观测壳层，斜率 0.02 才是候选的贡献。**
换句话说，融合后的可见 IoU 几乎不携带关于生成几何的信息；
“配准失败但融合后通过”的候选有 47 个。

原因写在每个融合清单里（`scripts/fuse_observed.py:818` 附近生成的 note）：

> `H5-F = 观测约束 + Lux3D 父候选隐藏几何；可见面由构造得到，不证明 Lux3D 自己重建准确。`

而**唯一正式资格门**恰好只用融合后指标：
`scripts/candidate_qualification.py:284-308` 的 `visible_pass` 读的是
`proc['fusion_metrics']['mask_iou' / 'vis_pt_p95_mm' / 'freespace_violation']`，
全文没有任何对 `align` 的引用。

**后果**：
1. `qualified` / `visible_pass` 不能发现候选几何错误；
2. 主表的 `strict.pass` 列不是质量列，是“壳层覆盖度”列；
3. 所有基于“strict 通过 → 候选可用”的表述（含 V6 以来多份结论）都需要重新表述。

### P0-4 验收门通不过自己的真值对照，且改分辨率后没有重新标定

`reports/v2/key_states/truth_parent.fused.manifest.json`（真值网格经 align24 作父先验）：

**建议**：把阈值移进冻结配置，用“真值对照 + 固定裕量”一次性标定（例如
`freespace_max = truth_freespace + 0.02`），并在所有清单里记录阈值来源。
在标定完成前，`strict.pass` 只能当诊断量、不能当门禁量。

**`libc++abi: __cxa_guard_acquire detected recursive initialization` → 进程 SIGSEGV**。
整个 discover 因此中断，`test_candidate_store` 之后的用例一个都没跑。

`tests/test_camera.py:4` 的 docstring 自己写了要 `MUJOCO_GL=osmesa`，
但本机 `MUJOCO_GL=osmesa` 也会失败（`PyOpenGL … 'NoneType' object has no attribute 'glGetError'`，
缺 OSMesa 运行时）。

需要说清楚：CNB 沙箱里 `MUJOCO_GL=osmesa` 是配好的（`.cnb/smoke.sh` 专门验证渲染），
所以这些用例在沙箱里大概率是绿的。**问题不在“代码坏了”，而在“测试不隔离 + 影响面失控”**：
一个依赖图形栈的用例不该让整轮 discover 以 SIGSEGV 结束，应该 skip 或只在显式环境下收集。

### 4.2 去掉 camera 之后仍不绿，且很慢

```

```

唯一 error 是 `tests/test_freespace.py:26` 用 `subprocess` 调 `scripts/observe.py`，
后者要 GL 渲染。即：**第二个测试也硬依赖图形栈**。

建议：
- 用 `@unittest.skipUnless(os.environ.get('MUJOCO_GL'))` 或 `has_display()` 显式跳过，
  而不是让环境问题变成 core dump / error；

`scripts/verify_delivery_r1.py`（我已实跑：**73/73 PASS**，这条是真的），
