## 0. 项目的两个核心，以及这一版改了什么

### 0.1 两个核心

1. **Lux3D 把一张照片变成"看不见的那一面"。** 机器人停在石头前，只看得到正面。Lux3D 根据照片生成整块石头；机器人用观测给它配准、自检，自检通过的想象才参与通行决策。这是比赛的核心，也是成片的主线。
2. **月面影子。** 月球没有大气，影子几乎全黑、边缘锐利；月球南极太阳高度最高约 1.5°，影子拖得很长。只看二维照片，会把影子和石头看反：
   - 影子被当成石头的一部分：送进 Lux3D 的图里，石头被拉长、变形；
   - 石头背光的一面被当成影子：去影子时把石头本身抹掉，机器人以为前方是空地。

   我们的做法：机器人有深度相机。影子贴在地面上，石头高出地面。用深度拟合地面、按离地高度分割石头，完全不看亮度，影子天然被排除，背光的石头面也不会丢。本版把它接进了观测流程，并设计了一组实验，用真实的 Lux3D 调用检验影子对想象的影响（§3.4）。

   负责人已渲染的 12 个条件（3 块岩石 × 4 种太阳角度，见 §3.4）里，分割结果如下（与渲染器给出的真实石头像素比较）：

   | 太阳 | 深度分割 IoU | 只看亮度的"物体" IoU | 亮度"物体"是真石头的几倍 | 只看亮度去影子后，石头还剩 |
   | --- | --- | --- | --- | --- |
   | 高太阳侧光 | 0.98 | 0.89–0.92 | 1.1 | 76–84% |
   | 低太阳侧光 | 0.98 | 0.41–0.50 | 2.0–2.4 | 38–72% |
   | 低太阳在身后 | 0.98 | 0.27–0.32 | 3.1–3.7 | 45–46% |
   | 低太阳逆光 | 0.98 | 0.999 | 1.0 | 2–5% |

   两种"看反"都出现了：影子被并进石头（最多 3.7 倍），或者石头被当成影子抹掉（只剩 2–5%）。深度分割在所有条件下都是 0.98。

### 0.2 改动

1. **代码归负责人。** 观测、遭遇决策、路线驱动、联系表、影子实验的代码由负责人编写。你的工作是原样运行、调用 Lux3D、把数据拉回本地并推送。

   - 负责人环境里的测试状态见 §0.3。
2. **机器人的照片改用月面渲染器（`v7_visual.py`）。** 同一份 MJCF，只换外观：
   - 扫描岩石带贴图、两面渲染，不再出现空心环或碎片；
   - 月壤地面、远山、地球、星空；
   - 车道外有装饰碎石，不参与物理；
   - 太阳为单一方向光，带锐利阴影。

   所有参与碰撞的几何、body 和 joint 都不变，qpos 可以逐帧拷贝。
3. **观测（`v7_observe.py`）沿用 v3 的采集规则，岩石掩码改由深度给出（`v7_shadow.py`）：**
   - 停车点与岩石的相对位置照搬 v3 状态，相机为机身前 0.42 m、俯 24.83°、fovy 70；
   - 4040×3030 生成图，用 `v3_obs._variants` 生成 A/B/C 三类输入；
   - 掩码 = 离地高度 > 1.5 cm、位于车道前方的最大连通块。地面由 RANSAC 拟合；
   - 渲染器的分割图只用来核对：深度掩码与分割的 IoU 写进 `observation.json` 的 `mask_check`，低于 0.9 时程序报错停止。负责人测试中为 0.98。
4. **遭遇决策（`v7_encounter.py`）全部调用已验证模块：**
   - `v3_fuse`、`v3_register`、`v5_core`、`v5_eval.robust_arm`、`plan_detour`；
   - 每份准入候选各自预演，多数投票，同时报告最坏规则；
   - OBS_CONS 在两种极端几何上用同一份计划，取交集；
   - 零准入时回退。
5. **路线驱动（`v7_route.py`）：**
   - 一次连续仿真，可断点续跑；
   - 动作只来自 `decision.json`；
   - 每一帧都有真实的 action / phase 标签；
   - `lux_request.json` 里的路径一律是仓库相对路径。
6. **仿真核心有一处补丁（`v3_core_detour_params.diff`）。** 修正前，绕行的几何计划（`offset_m` / `leave_x`）从未传进 Detour 动作（`run_action` 没把 plan 交给 `EpisodeRunner`）。V5 A 线的"按几何规划绕行"实际只影响了"能不能绕"，没有影响"怎么绕"。
   - 补丁让 D1/D2 在预演和执行中都真正使用计划。
   - 已知局限（负责人的 KA9 实测）：绕行的横向响应滞后约 1 m，偏移 0.75 m 时有超调。这是导航底座增益造成的，本版不改，只如实记录。
7. **仿真环境对 `mesh_file` 物体不会按 `target_height_m` 缩放**（`wheelleg_env` 只对带清单的资产缩放）。
   - route2 的 E1 写的是 0.172 m，实际用的是 h1 网格的原生高度，碰巧一致。
   - 负责人第一次测试时，碎石按原生 h0 网格放进场景（12–24 cm），机器人被卡死在碎石区。
   - v7 的岩石网格一律先按目标高度缩放好再放进场景（`lunar_world.rock_asset_scaled`），不再写 `target_height_m`。

## 1. 数据保管（硬约束）

**沙箱的销毁不可逆，而且有时限。本地机器才是数据的唯一可靠存放处。**

1. **本地生成，沙箱只做计算。** 输入（代码、场景、观测、Lux3D 结果）从本地推到沙箱；沙箱跑完立即拉回本地。
2. **每完成一个阶段就拉回，不要攒到最后。** 阶段指：
   - 一次 `v7_route.py` 调用结束（退出码 0 或 10）；
   - 一次 `v7_shadow_exp.py` 调用结束；
   - 一次渲染批次结束。
3. **拉回后在本地校验 sha256**，再提交并推送到 GitHub。大文件（png、npy、npz、glb、stl）走 LFS。之后才能在沙箱上继续下一步。
4. **`docs/v7/SANDBOX_LOG.md` 每次沙箱作业追加一行：**

   | 字段 | 内容 |
   | --- | --- |
   | 沙箱 id | 本次使用的沙箱 |
   | 开始时刻 | 作业开始时间 |
   | 结束时刻 | 作业结束时间 |
   | 命令 | 执行的完整命令 |
   | 拉回的目录 | 拉回本地的目录列表 |
   | 文件数与总字节 | 拉回内容的规模 |
   | sha 校验 | 校验结果 |
   | 推送提交号 | 对应的 GitHub 提交 |

5. **沙箱里不留唯一副本。** 沙箱被回收时，任何还没拉回的数据都视为丢失，要重跑。
6. **Lux3D 调用只在本地执行**（密钥在本地环境变量），结果直接存本地，再推给沙箱。
7. **分工：**
   - 本地 4 核 8G：Lux3D 调用、git、LFS、联系表、轻量检查；
   - 沙箱 8 核 16G：路线仿真、预演、影子实验的渲染与评估、成片渲染。

### 3.3 规则

- **路线断点续跑要求仓库根路径完全相同。** 环境的场景签名包含文件的绝对路径，换了路径，`same_scene` 恢复会被拒绝。
  - 沙箱一律使用同一个根路径（例如 `/workspace/lunar-lab`）。
  - 沙箱被回收、换新沙箱时，用同一路径克隆、拉回最新数据后再续跑。
  - 不得把恢复方式改成 `project` 来绕过。
- **入库方式：**
  - 在 `.gitattributes` 加 LFS 规则：`runs/v7/**/*.png`、`runs/v7/**/*.npy`、`runs/v7/**/*.npz`、`runs/v7/**/*.stl`、`assets/v7/**/*.glb`；
  - JSON、CSV、MD 走普通 git；
  - `runs/v7/cache/` 不入库（可重建）。
  - 负责人的测试里，只看正面那一臂的运行目录约 180 MB、8600 个文件，绝大部分是预演记录。正式运行会更大，照样整目录入库。
- 服务端失败可以重提一次，标 `retry_of`，仍失败就把该任务记为 failed 写进结果，让流程继续；准入只看拿到的候选。
- 不得替换输入图，不得挑选候选。
- 曝光规则沿用 V5：均值 <100 才提亮。影子实验的输入一律不提亮（暗是实验条件本身）。

### 3.4 影子实验

**问题：** 影子会不会让 Lux3D 把石头想错？用深度去掉影子，能不能纠正？

**设计：** 3 块扫描岩石（`moon_rock_02`、`moon_rock_05`、`moon_rock_07`，均缩放到 0.2236 m 高）× 4 种太阳角度：

| 条件 | 太阳 | 照片里发生什么 |
| --- | --- | --- |
| `high_side` | 高太阳，侧光 | 对照：影子短 |
| `low_side` | 约 10°，侧光 | 影子横向拖长，与石头背光面连成一片 |
| `low_front` | 约 11°，在机器人身后 | 石头的影子拖向远处，机器人自己的影子也伸向石头 |
| `low_behind` | 约 11°，逆光 | 石头朝向相机的一面全黑 |

每个条件拍同一张照片、做同一份观测（深度掩码），只改送进 Lux3D 的输入图：

| 输入 | 含义 |
| --- | --- |
| `A_naive` | 只看亮度时的"物体"框出的原图紧裁剪，影子在框内 |
| `B_naive` | 只看亮度时的"物体"（石头 + 与之相连的暗区）抠图 |
| `B_depth` | 深度判定的石头抠图，影子已去掉（本项目的做法） |

每种输入提交 2 次，每个条件 6 个任务，全部 12 个条件共 72 个任务。配准、准入和真值比较对三种输入完全相同，差别只来自输入图。

**步骤：**

1. **沙箱：** 生成观测与请求。

   ```
   MUJOCO_GL=egl python3 scripts/v7/v7_shadow_exp.py --prepare --out runs/v7/shadow_exp
   ```

   每个条件目录 `runs/v7/shadow_exp/<rock>/<sun>/` 下有：
   - `photo.png`：机器人拍到的照片；
   - `overlay.png`：绿 = 深度判定的石头，红 = 只看亮度时多算进来的部分；
   - `obs/`：观测；
   - `inputs/`：6 张输入图；
   - `stats.json`：分割统计；
   - `lux_request.json`。

   每块岩石还有 `truth_world.stl`（真值网格，只用于评估）。拉回、校验、推送。

2. **本地试点：** 只做 `moon_rock_02` 的 4 个条件（24 个任务）。
   - 按 `docs/v6/LUX3D_CALL.md` 提交，`mode=img`，每个 item 一张图、一个任务。
   - GLB 存 `assets/v7/lux/<task_id>/tex_mesh.glb`，写请求里 `result_file` 指定的 `lux_result.json`，推送。
3. **沙箱：** 拉取后评估。

   ```
   python3 scripts/v7/v7_shadow_exp.py --evaluate --out runs/v7/shadow_exp
   ```

   输出 `eval_rows.json`（每个任务一行：准入指标、是否准入、背面误差、占地比、隐藏区 IoU）和 `summary.json`（按 输入 × 太阳 汇总）。拉回、校验、推送。
4. **回报试点，停下等负责人看图。** 负责人确认后，再做另外两块岩石（48 个任务），重复第 2、3 步。`--evaluate` 会重新评估所有已有结果的条件，可以重复运行。
